## How `main` works (checked 9 Oct 2026)

- `api.py` is the FastAPI app. Endpoints: `GET /health`, `POST /evidence`, `GET /product/{product_id}`, `GET /products`.
- `POST /evidence` serves `evidence_store.json` only and returns 404 on a miss. It never runs the crew, despite an outdated docstring and README saying otherwise.
- `evidence_store.json` holds precomputed evidence (93 entries). It is generated by `precompute.py`, which runs the CrewAI crew and costs money. `api.py` only reads it.
- `dataset.py` downloads the dataset CSVs from Hugging Face **at import time**. Importing `api.py` therefore needs network access.
- `dataset.match_store_key()` matches in the order exact, alias, modifier, none, and the result is disclosed to callers as `match_type`. Looser rules can never shadow a real name. Fuzzy matching was ruled out because it fails silently.
- `dataset.normalise()` lowercases, turns hyphens into spaces, removes apostrophes and collapses whitespace. `/product` matching depends on it.
- `guardrails.py` holds `BANNED_PHRASES` and `find_banned_phrases()`, shared by the API and the eval so they cannot drift. Matching is substring-based by design.
- `src/lagomy/` is the CrewAI crew. The claims-register feature does not involve it.
- `README.md` is partly out of date. Where the README and the code disagree, the code is the truth. Report the disagreement; don't fix the README unless asked.
- There is no pytest suite on `main` yet.
- `test_tavily.py` and `test_vision.py` at the root are **not tests**. They make live, paid API calls when imported. Never run bare `pytest` from the root, because it would collect them.
- `knowledge/user_preference.txt` is CrewAI scaffold placeholder text. Ignore it.

## Architecture rules

- Generate at build time, serve at request time. Scripts produce JSON files; `api.py` only reads them.
- No model calls, web requests or searches at request time on `main`.
- No new API keys, environment variables or paid services on `main`.
- Existing endpoints keep their paths, request and response models, and behaviour. New behaviour goes in new endpoints and new modules.
- Put claims-register logic in its own module (for example `claims_register.py`) that does **not** import `dataset.py`, so it can be tested without network access.
- Do not change `dataset.py`, `guardrails.py`, `evidence_store.json`, `precompute.py` or anything in `src/lagomy/` unless the task says so.
- No new runtime dependencies without asking. Adding pytest as a dev dependency (`uv add --dev pytest`) is fine; it matches the hackathon branch.

## The claims-register feature

**What it is:** a lookup of a claim's wording against the Great Britain nutrition and health claims (NHC) register, reporting what the register records.

**What it is not:**
- not a determination that a product or label is legally compliant. Finding a claim on the register does not establish that any product meets that claim's conditions of use.
- not a judgement of whether a claim is true, or of whether a product is any good.
- not advice.

**Never** describe a result as compliant, non-compliant, legal, illegal, valid, invalid, approved for this product, supported, unsupported, an overclaim, misleading or accurate. Report the register's own recorded status in the register's own words.

**Reference source:**
- The GB NHC register only. Not the EU register: GB diverged from it in January 2021.
- Not `evidence_store.json`. The evidence store answers a different question (what NHS, NICE and BNF say about an ingredient) and must not be used to judge claims.

**Register data:**
- The register file is not in the repository yet. Do not download it, do not recreate register entries from memory or training data, and do not guess its column names.
- Ingesting the register is a separate task. Chantal will supply the file.
- Until then, tests use a small fixture of **invented** substances and claims (for example "Testium contributes to the normal function of fixtures"), so fixture data can never be mistaken for real register data.

**Response fields:**
- the claim exactly as entered
- the register wording, verbatim
- the substance the claim concerns
- the register status, as the register records it
- the conditions of use, verbatim
- the register identifier
- `match_type`: `exact`, `normalised` or `none`

**Verbatim means verbatim.** Never paraphrase, summarise, correct, trim or tidy register text or the entered claim. A typo in the entered claim stays in the response.

**Matching:**
- Try exact first, then normalised.
- No fuzzy matching, similarity scores, confidence values, embeddings, model calls, or substring/contains matching.
- If more than one register entry matches, return all of them. Do not pick one.
- Every match carries its `match_type`, so callers can see how it was found.

**What `normalised` ignores:** letter case, punctuation and runs of whitespace. Nothing else.
- Words are never ignored. "contributes to a reduction" and "contributes to the reduction" are **not** a normalised match.
- Define the claims normaliser inside the claims module. Do not reuse or change `dataset.normalise()`, because changing it would change `/product` matching.
- Only Chantal can widen this definition, by editing this file.

**Prose:** prefer fixed field values to sentences. Any message string in a response must pass `find_banned_phrases()`.

## Data and privacy

- The dataset CSVs are CC BY-NC and are served from Hugging Face. Never commit them, copies of them, or samples derived from them. That includes `product_claims.csv`.
- No `user_id`, account, session or other identifier in any schema. The API is stateless. Do not log request bodies to disk.
- Never read, print or commit `.env`.

## Tests

- New tests go in `tests/`. Run them with `uv run pytest tests/`.
- Tests must pass offline: no Hugging Face, no network, no API keys.
- Endpoint tests that import `api.py` need `dataset.py` stubbed before import. Propose the stubbing approach in your plan before writing it. Making dataset loading lazy would change existing behaviour, so it needs Chantal's approval.
- Every new behaviour gets a test. Claims-register tests must cover at least:
  - an exact match
  - a normalised match (case, punctuation, whitespace)
  - an article difference ("a" vs "the") returning `none`
  - a miss returning `none` with no invented register fields
  - register wording and the entered claim returned byte-for-byte unchanged
  - more than one matching entry, all returned
  - no forbidden verdict word anywhere in any response
- Never weaken, skip or delete a test to make it pass. If a test looks wrong, say so and stop.
